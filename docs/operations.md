# Мониторинг и нагрузочная проверка

## Показатели

Prometheus собирает /metrics каждые 15 секунд
API проверяет совместимость выпуска и PostgreSQL при каждом сборе
Grafana получает источник и dashboard автоматически из deployment/grafana

| Показатель | Смысл |
| --- | --- |
| HTTP RPS и статусы | Все завершившиеся поисковые ответы, включая 429 |
| p50/p95/p99 | Квантили времени HTTP-ответа |
| Этапы p95 | queue, validate_release, bm25, encoder, dense, documents, опционально rerank |
| active / waiting | Фактически вычисляемые задачи и ожидание слота |
| Отказы очереди | full, wait_timeout, execution_timeout |
| Redis | hit, miss, invalid, error, oversize и время чтения/записи |
| ready | Совместимы ли обязательная база и загруженный выпуск |
| CPU | Количество использованных ядер процессом API, а не процент всей машины |
| RSS | Резидентная память процесса API |

Время этапа учитывается и при исключении или отмене
После HTTP-таймаута active остаётся ненулевым до окончания реального вычисления
Выпуск также доступен в nlp_ranker_release_info и ответе поиска
Метрики относятся к одному процессу; несколько workers требуют отдельной настройки
В Redis hit ratio не включены ошибки записи и слишком большие записи
HTTP-квантили Prometheus приблизительны и зависят от границ histogram buckets

## Предупреждения

- RankerApiUnavailable: сбор метрик недоступен не менее 2 минут
- RankerSearchNotReady: база или выпуск не готовы не менее 2 минут
- RankerSearchErrors: серверные ошибки поиска сохраняются не менее 2 минут

`make monitoring-check` проверяет синтаксис и сценарии отказа/нормальной работы
Порог задержки пока не задан: замеры ниже не являются согласованным SLA
Alertmanager и внешняя доставка сообщений не настроены
Состояние правил можно посмотреть в Prometheus по адресу /alerts

## Условия замера 8 октября 2026 года

- AMD Ryzen 7 7840HS, около 27 GiB доступной системе RAM, Linux, инференс на CPU
- API в Docker, один Uvicorn worker, E5-small CPU с 4 потоками
- Корпус: 2058 документов, 2519 фрагментов; BM25 + E5 + RRF
- 1 активный поиск, 8 ожидающих; ожидание до 1 с, выполнение до 10 с
- PostgreSQL: пул 5, до 5 дополнительных соединений; Redis: до 10 соединений
- Locust выполняется на той же машине; учитывается локальный HTTP и полный ответ
- По 30 с для 1, 4, 16 пользователей; скорость подключения 8 пользователей/с
- Пауза пользователя 50-150 мс; это закрытая модель нагрузки, фиксированный RPS не задаётся
- mixed: 30% повтор фиксированного запроса, остальные случайные сочетания технологий
  Часть запросов использует remote; генератор может повторить уже созданный запрос
- cached: все пользователи отправляют один запрос с одинаковым limit и фильтрами
- Перед серией очищены только ключи кеша поиска nlp_ranker:search:v1:*
- Готовность, очередь, CPU и RSS дополнительно снимались через /metrics раз в секунду
  Эта проверка тоже использует PostgreSQL; максимумы очереди являются максимумами снимков
- Финальная серия выполнена после завершения pytest, сборки и проверки выпуска

Перезапуск API до /health/ready занял 15,565 с, включая остановку процесса
Веса уже находились в volume; время первой загрузки из интернета не измерялось

## Повторение

```bash
make monitoring-up
make load-test LOAD_USERS=1 LOAD_DURATION=30s LOAD_SPAWN_RATE=8 LOAD_MODE=mixed LOAD_REPORT=artifacts/reports/load-mixed-1
make load-test LOAD_USERS=4 LOAD_DURATION=30s LOAD_SPAWN_RATE=8 LOAD_MODE=mixed LOAD_REPORT=artifacts/reports/load-mixed-4
make load-test LOAD_USERS=16 LOAD_DURATION=30s LOAD_SPAWN_RATE=8 LOAD_MODE=mixed LOAD_REPORT=artifacts/reports/load-mixed-16
make load-test LOAD_USERS=4 LOAD_DURATION=30s LOAD_SPAWN_RATE=8 LOAD_MODE=cached LOAD_REPORT=artifacts/reports/load-cached-4
```

По умолчанию LOAD_SPAWN_RATE=1; команды выше повторяют скорость этого замера
Не запускайте параллельно pytest, построение индексов и другие CPU-эксперименты
После нагрузки проверьте /health/ready и обычный запрос через UI
