# План реализации NLP Ranking

План охватывает путь от выбора данных до работающего поиска через API и Streamlit.
Статус завершённых блоков указан отдельно. Остальные пункты описывают предстоящую работу.
Первая версия реализована: корпус, поиск, API, интерфейс, хранилища и мониторинг
CI/CD исключён; брокер и дообучение остаются будущими блоками

Работаем в `/home/aikira/Рабочий стол/projects/nlp_ranking`. Коммиты и staging
запрещены. Все описания и docstring - на русском; комментарии в Python не используются.
Папки создаются только по мере роста настоящего кода. Этот план не требует новых
модулей под каждый пункт: начинаем с существующих файлов

## 3. Pydantic, конфигурации и structlog

Статус: выполнен 7 октября 2026 года

Схемы текущих YAML размещены в соответствующих модулях, без новых каталогов.
Проверяются неизвестные ключи, типы, диапазоны, число кандидатов, отдельные пути
обучения/валидации и совместный выбор базового отчёта и порога качества.
Параметры ещё не выбранных моделей и отложенного обучения допускают null.
Настройки окружения проверяют форматы логов, лимиты пулов и адреса сервисов.
CLI проверяет схему выбранного этапа, сообщает неверные поля без значений,
логирует исход и длительность; dry-run не записывает артефакты.
logging, structlog и логи сервера имеют общий формат; Compose задаёт JSON.
Чистый ASGI middleware создаёт request_id, возвращает его в заголовке,
логирует шаблон маршрута и очищает контекст, включая ошибки. Непредвиденный
ответ 500 также содержит request_id и общее сообщение. Не выводятся тело,
строка запроса и traceback. Проверены 16 одновременных запросов, перенос
контекста в поток, отказ CLI, ошибки HTTP и обычный logging.
Полные настройки этапов уточняются при реализации их поведения; в этом блоке
не выбирались датасет, модели и пороги качества

1. Разделить настройки окружения и параметры эксперимента: адреса/секреты в окружении,
   параметры обработки и поиска - в YAML.
2. По мере реализации описать отдельные Pydantic-схемы этапов внутри их модулей.
3. Проверять диапазоны, обязательные параметры и неизвестные ключи до запуска работы.
4. Сделать dry-run проверкой полной схемы конкретного этапа, без записи артефактов.
5. Настроить structlog и logging: читаемый вывод локально, JSON в контейнерах.
6. Добавить события запуска, завершения и ошибки этапа с длительностью и версией данных.
7. Для API создать request_id, очистить контекст в начале запроса и вернуть ID в заголовке.
8. Проверить разделение контекстов параллельных запросов и передачу контекста в потоки;
   не записывать секреты и полные тексты запросов в обычные логи

Готово, когда неверный конфиг останавливает запуск с понятной причиной,
а по логам можно восстановить путь одного запроса или этапа обработки

## 25. Kafka или другой брокер - будущий блок

Kafka не входит в первую версию и сейчас не устанавливается. Этот блок описывает
следующий шаг для автоматического обновления вакансий, если такой сценарий выбран.
Сам брокер и Python-клиент ещё не утверждены

1. Описать реальные события и требования: обновление/удаление вакансии, допустимая
   задержка, необходимость повторного чтения истории и порядок обработки.
2. Сравнить Kafka с более простой очередью по этим требованиям и ресурсам компьютера.
3. После выбора добавить отдельный профиль Compose, настройки и проверки клиента.
4. Описать сообщение: event_id, document_id, версия, тип события и версия схемы.
5. Если выбрана Kafka, определить topics, partition key и порядок событий одного документа.
6. Для изменения БД и публикации события продумать transactional outbox;
   подтвердить необходимость реальным сценарием, а не добавлять заранее.
7. Реализовать обработчик с идемпотентностью и проверкой версии: старое событие
   не перезаписывает новый документ или вектор.
8. Подтверждать обработку после успешной записи; проверить повтор доставки,
   падение воркера, retry и очередь необрабатываемых сообщений.
9. Проверить согласованность корпуса, поискового индекса и кеша после обновления.
10. Добавить метрики отставания, времени обработки и ошибок, затем тест восстановления

Готово, когда обновления выполняются автоматически и повтор доставки безопасен.
Транзакции Kafka не означают атомарную запись во внешнюю PostgreSQL/MinIO;
гарантии зависят от всего сценария обработки.
[Гарантии Kafka](https://kafka.apache.org/41/design/design/)

## Правила реализации и паттерны

| Задача | Подход | Ограничение |
| --- | --- | --- |
| Сборка приложения | Фабричная функция create_app и явная передача зависимостей | Без универсальной фабрики классов |
| Замена поиска | SearchBackend как Strategy | Интерфейс расширяется только вместе с реальным сценарием |
| Доступ к документам | DocumentRepository | Транзакцией владеет вызывающий сценарий |
| Ресурсы процесса | lifespan и AsyncExitStack | Очистка регистрируется сразу после создания |
| Кеширование | Внешняя обёртка или отдельная функция при необходимости | Redis не проникает в математические алгоритмы |
| Артефакты | Узкая интеграция MinIO и manifest версии | Без универсального слоя для всех возможных хранилищ |
| Обновление событий | Outbox и идемпотентный обработчик при выбранном брокере | Не реализуется до блока 25 |

После реализации блоков 16-18 выполнено разделение серверного кода на
controller, service, model и repository. SearchService управляет рабочим поиском;
DocumentService читает актуальные документы отдельно от индекса. SQL вынесен
в репозитории, загрузка моделей в ml/inference, этапы подготовки и оценки в pipelines.
Очередь ограничивает CPU-нагрузку и удерживает слот при отмене. Полное дерево
и обязанности компонентов описаны в docs/architecture.md
